# DX12 메모리 최적화 데모

발표 **"DX12 메모리 구조 이해하기"** 때 옆에 띄워 두고 직접 조작하는 데모입니다.

- **왼쪽**: 렌더링 화면. 가운데에 무거운 행성 메시가 있고, 큐브 수천 개가 그 주위를 돕니다.
- **오른쪽**: 설정 패널. 시나리오마다 "최악 ↔ 최적"을 클릭 한 번으로 바꿉니다.
- **화면 왼쪽 위 큰 글씨**: FPS, CPU/GPU 시간, VRAM, 공유 GPU 메모리, 시스템 RAM. 청중이 멀리서도 볼 수 있게 크게 띄웁니다.

데이터가 지나가는 길은 발표 순서와 같습니다.

```
CPU 원본(std::vector, 시스템 RAM) → Upload Heap(시스템 RAM) → Default Heap(VRAM)
→ GPU가 읽고 그림 → 렌더 타깃 → 스왑체인 Present → 모니터
```

## 1. 빌드하고 실행하기

### 준비물 (한 번만)

1. **Windows 10 또는 11 (64비트)**, DX12를 지원하는 그래픽카드
2. **Visual Studio 2026 또는 2022** (Community 버전은 무료)
   - 설치할 때 **"C++를 사용한 데스크톱 개발"** 워크로드에 체크하세요.
   - 이 워크로드에 CMake와 Windows SDK가 같이 들어 있어서 따로 설치할 것이 없습니다.
3. 처음 빌드할 때 **인터넷 연결**. Agility SDK(최신 D3D12 런타임, 약 20MB)를 nuget.org에서 자동으로 받습니다.

### 방법 A: 더블클릭 한 번 (추천)

1. 이 폴더 전체를 PC에 복사합니다. 경로에 한글이 없는 곳이 안전합니다. 예: `C:\dev\memdemo`
2. 폴더 안의 **`build.bat`** 을 더블클릭합니다. (일반 cmd에서 `build.bat` 을 실행해도 됩니다.)
   - `cmake`가 PATH에 없으면 설치된 Visual Studio를 찾아 개발자 환경(CMake, 컴파일러)을 자동으로 불러옵니다.
   - 처음 구성할 때 `Could not create named generator Visual Studio 18 2026` 이 보일 수 있습니다. VS 2022에서는 정상이고, 바로 2022로 다시 시도합니다.
3. 빌드가 끝나면 데모가 자동으로 켜집니다. 다음부터는 `build\Release\DX12MemoryDemo.exe` 를 바로 실행하면 됩니다.

### 방법 B: Visual Studio에서 열기

1. Visual Studio 2026 또는 2022 → **파일 → 열기 → 폴더...** → 이 폴더를 선택합니다.
2. VS가 `CMakeLists.txt` 를 읽고 자동으로 구성합니다. 아래 "출력" 창에 `Agility SDK 1.619.6: ON` 이 보이면 정상입니다.
3. 위쪽 구성 드롭다운을 **x64-Release** 로 바꿉니다. 발표 숫자는 반드시 Release로 재세요. Debug는 훨씬 느립니다.
4. 시작 항목을 **DX12MemoryDemo.exe** 로 고르고 ▶ 버튼을 누릅니다.

> Debug 빌드에서는 D3D12 디버그 레이어가 켜집니다. 잘못된 사용이 있으면 VS 출력 창에 경고가 뜹니다.

### 실행 파일만 다른 PC로 옮길 때 (배포)

Release로 빌드한 뒤 `build\Release\` 폴더에서 **아래 두 가지만** 같은 구조로 복사해 주면 됩니다.

```
DX12MemoryDemo\
├─ DX12MemoryDemo.exe
└─ D3D12\
   ├─ D3D12Core.dll
   └─ d3d12SDKLayers.dll
```

- `D3D12` 폴더가 없어도 실행은 되지만, GPU Upload 힙(ReBAR) 항목이 꺼질 수 있습니다. 폴더 이름과 위치(exe 바로 옆)를 바꾸지 마세요.
- C++ 런타임은 exe 안에 들어 있어서(`/MT`) 따로 설치할 것이 없습니다.
- 셰이더 컴파일러(`d3dcompiler_47.dll`)와 한글 글꼴(맑은 고딕)은 Windows 10/11에 기본으로 있습니다.
- 받는 사람 조건: Windows 10/11 64비트, DX12 그래픽카드, 최신 그래픽 드라이버.
- 다른 파일(`.pdb`, `.lib`, `imgui.ini` 등)은 필요 없습니다. 코드까지 주려면 `memdemo.zip` 전체를 주세요(받는 사람이 `build.bat`으로 빌드).

## 2. 화면 사용법

| 조작 | 하는 일 |
|---|---|
| **F1** / "전부 최악" 버튼 | 1~8번과 10번(밉맵 끔, 매 프레임 새로 만들기) 시나리오를 모두 최악으로 바꿉니다. 텍스처 크기는 그대로 둡니다 |
| **F2** / "전부 최적" 버튼 | 1~8번과 10번 시나리오를 모두 최적으로 바꿉니다 |
| **F3** | 패널을 숨기거나 다시 보여 줍니다 (렌더 화면을 크게) |
| **F4** / "와이어프레임 보기" | 메시를 면 ↔ 삼각형 테두리(와이어프레임)로 바꿉니다. 행성 삼각형이 많으면 선이 빽빽해서 면처럼 보이니 20~50(천 개)으로 낮춰 보세요 |
| **F5** / "평균 다시 모으기" | 평균을 지금부터 새로 모읍니다. 설정을 바꾸면 자동으로도 새로 모읍니다 |
| "평균 구간" 슬라이더 | FPS와 시간을 몇 초 동안 평균 낼지 정합니다 (0.5~10초, 기본 5초). 화면 위 큰 글씨도 이 평균입니다 |
| "글자 크기" 슬라이더 | 프로젝터용으로 패널 글자를 키웁니다 |
| "화면 오른쪽 위에 그래프 보기" | 렌더 화면 오른쪽 위에 CPU 프레임 시간과 GPU 시간 그래프를 띄웁니다. F3로 패널을 숨겨도 보입니다. 세로 범위는 자동이고, 점선은 60 FPS(16.7ms) 기준선입니다. 화면이 좁아 왼쪽 위 큰 글씨와 겹치면 그 아래로 내려갑니다 |
| "코드 변수 이름 보기" | 각 설정 아래에 `코드: s.meshHeap = MH_DEFAULT · [시나리오 1] RebuildMesh()` 처럼 **이 설정이 바꾸는 코드 변수, 지금 값, 그 값을 쓰는 곳**을 보여 줍니다. 기본은 켜짐이고, 발표 화면을 깔끔하게 하려면 끄세요 |
| 각 항목 옆 **(?)** | 마우스를 올리면 쉬운 설명이 나옵니다. **클릭하면 패널 안에 펼쳐 두고**, "(접기)"를 누르면 닫힙니다 |
| 패널 왼쪽 경계선 | **좌우로 드래그**해서 패널 폭을 바꿉니다. 더블클릭하면 기본 폭으로 돌아갑니다 |

각 시나리오 아래에는 초록색 **"최적: …"** 이나 빨간색 **"최악: …"** 이 표시됩니다. 지금 어떤 상태인지 청중에게 바로 보여 줄 수 있습니다.

**비교할 때는 VSync를 끄세요.** (기본값이 꺼짐입니다.) VSync를 켜면 FPS가 모니터 주사율(예: 60)에 묶여서 차이가 숫자로 안 보입니다.

## 3. 시나리오 10개와 발표 시연 순서

슬라이드 번호는 45장짜리 현재 덱 기준입니다. 숫자가 얼마나 차이 나는지는 GPU마다 다르니, **발표 PC에서 미리 한 번 돌려 보고** 가장 극적인 값을 메모해 두세요.

### 1. 정점 데이터 위치 (슬라이드 5–8, 10–11)

- **바꾸는 것**: 행성 메시 버퍼를 Upload 힙 / Default 힙 / GPU Upload 힙 중 어디에 둘지, 그리고 "매 프레임 CPU에서 다시 보내기"를 할지.
- **최악**: Upload 힙 + 매 프레임 다시 보내기. CPU는 매 프레임 수십 MB를 memcpy 하고, GPU는 PCIe 너머 시스템 RAM에서 정점을 읽습니다.
- **최적**: Default 힙(VRAM)에 한 번만 올리기.
- **볼 것**: "GPU: 행성 ms"가 크게 바뀝니다. "같은 자리에 반복 그리기"를 4~8로 올리면 차이가 더 커집니다. 다시 보내기를 켜면 "CPU 작업 ms"와 "Upload Heap" 메모리(프레임 수만큼 복사본)가 오릅니다.
- **시연 팁**: Upload 힙으로 바꾸는 순간 VRAM 막대는 그대로이고 "Upload Heap (시스템 RAM)" 줄과 Private 메모리가 오릅니다. "Upload 힙은 정말 시스템 RAM에 있다"를 눈으로 보여 주는 장면입니다.
- **GPU Upload 힙**은 ReBAR가 켜진 PC에서만 고를 수 있습니다. 회색이면 아래 "문제 해결"을 보세요.

### 2. 리소스 생성 (슬라이드 10)

- **최악**: 매 프레임 물체마다 작은 버퍼를 새로 만들기 (`CreateCommittedResource` 수천 번).
- **최적**: 미리 만든 큰 버퍼 하나를 재사용.
- **볼 것**: "이번 프레임에 만든 리소스" 숫자, CPU 작업 시간, 그리고 메모리 표의 "Upload Heap" 줄. 32바이트짜리 데이터도 버퍼 하나는 **최소 64KB**를 차지해서 메모리가 확 늘어납니다.

### 3. 배리어 (슬라이드 12)

- **최악**: 드로우 사이에 쓸데없는 배리어를 수백 번 끼우기 (깊이 버퍼를 "깊이 쓰기 → 셰이더 읽기 → 깊이 쓰기"로 왕복).
- **최적**: 0.
- **볼 것**: "GPU: 큐브 ms"와 배리어 숫자. GPU가 배리어마다 앞 작업을 끝내고 멈추기 때문에 GPU 시간이 늘어납니다. 차이는 GPU 제조사마다 다릅니다 (AMD에서 보통 더 큽니다).

### 4. CPU–GPU 동기화 (슬라이드 13, 23)

- **최악**: 동시에 진행할 프레임 수 = 1. 매 프레임 펜스로 GPU가 끝날 때까지 CPU가 기다립니다.
- **최적**: 2 또는 3.
- **볼 것**: "CPU: 대기 ms". 1로 바꾸면 대기가 커지고, CPU 시간과 GPU 시간이 더해진 만큼 프레임이 길어집니다.
- **차이를 크게 만드는 법**: CPU와 GPU가 **둘 다 비슷하게 바쁠 때** 차이가 가장 큽니다. "게임 로직 흉내 (CPU ms)"를 8로 두고, 행성 삼각형과 반복 횟수를 올려 GPU 시간도 8ms쯤 되게 맞추세요. 프레임 수 1이면 약 16ms(60 FPS), 2면 약 8ms(120 FPS)가 됩니다. 한쪽만 무거우면 겹쳐서 아낄 시간이 없어서 차이가 작습니다.

### 5. 드로우콜 (슬라이드 20)

- **최악**: 인스턴싱을 끄고 큐브 2만 개를 각각 그리기.
- **최적**: 인스턴싱으로 한 번에.
- **볼 것**: "드로우콜" 숫자(20000 ↔ 1)와 CPU 작업 시간.

### 6. PSO / 루트 시그니처 변경 (슬라이드 17, 부록 PSO)

- **최악 ①**: 드로우마다 PSO 두 개를 번갈아 바꾸고, 루트 시그니처와 모든 바인딩을 다시 걸기. 인스턴싱을 끈 상태에서 효과가 큽니다.
- **최악 ②**: 매 프레임 셰이더 컴파일 + PSO 새로 만들기. 게임의 "셰이더 컴파일 끊김"을 재현합니다.
- **최적**: PSO는 시작할 때 만들고 한 번만 설정.
- **차이를 크게 만드는 법**: 인스턴싱 끄기 + 큐브 20000개 + 행성 삼각형 0. 드로우 1개당 비용은 작아서 개수가 많아야 쌓여 보이고, GPU가 한가해야 CPU 비용이 FPS에 드러납니다. PSO B는 알파 블렌딩이 켜진 실제로 다른 상태입니다(화면은 같음).

### 7. GPU → CPU 되읽기 (슬라이드 6)

- **최악**: 매 프레임 화면을 Readback 힙으로 복사하고, 바로 펜스로 기다렸다가 읽기.
- **좋은 방법**: 매 프레임 읽되 몇 프레임 뒤에 확인하기. 결과는 늦게 받지만 아무도 기다리지 않습니다.
- **볼 것**: "CPU: 대기 ms", 그리고 되읽은 평균색이 "0프레임 전"인지 "3프레임 전"인지.

### 8. 스왑체인 / Present (슬라이드 23–24)

- 백 버퍼 2장 ↔ 3장, VSync 켬 ↔ 끔.
- **볼 것**: VSync를 켜면 "Present ms"가 커지고 FPS가 주사율에 묶입니다. 백 버퍼 한 장의 VRAM 크기도 표시됩니다.

### 9. VRAM 압박 실험 (따로 하는 실험, F1/F2에 포함되지 않음)

1. "추가 할당"을 VRAM 예산 근처까지 올립니다. 128MB씩 버퍼를 만듭니다.
2. VRAM 막대가 예산에 닿으면 노랑, 빨강으로 바뀝니다.
3. **"매 프레임 전부 사용하기"** 를 켜면, 예산을 넘긴 상태에서 OS가 메모리를 넣었다 뺐다(페이징) 하면서 프레임이 심하게 흔들립니다.
4. **"Evict 해 두기"** 를 켜면 VRAM 사용량이 내려갑니다. "안 쓰는 건 VRAM에서 빼도 된다"고 OS에 알려 주는 모습입니다.
5. 힙을 **Upload(시스템 RAM)** 로 바꾸면 VRAM은 그대로이고 공유 GPU 메모리와 이 프로그램 RAM이 오릅니다.

> 안전장치: 최대 할당은 VRAM 예산 + 1GB(Upload 힙은 시스템 RAM 3GB를 남기는 만큼)이고, "매 프레임 사용"은 한 프레임에 1GB씩만 돌아가며 씁니다. 한 프레임에 GPU가 2초 넘게 멈추면 Windows가 드라이버를 리셋(TDR)하고, 드라이버가 복구에 실패하면 파란 화면(`VIDEO_TDR_FAILURE`)이 날 수 있기 때문입니다. 실험이 끝나면 0으로 돌려 두세요.

### 10. 텍스처 (4K 텍스처 실험)

- **바꾸는 것**: 텍스처 크기(256 / 1K / 4K), 밉맵 만들기, 밉 단계마다 색 칠하기, 매 프레임 텍스처 새로 만들고 올리기. 텍스처는 파일 없이 코드로 만듭니다(체크무늬 + 16픽셀 격자 + 잡티). 기본값은 4K + 밉맵입니다.
- **최악**: 밉맵 없음 + 매 프레임 새로 만들기. 매 프레임 `CreateCommittedResource` + CPU가 64MB(밉맵 포함 85MB)를 Upload 힙에 쓰기 + `CopyTextureRegion` + 배리어.
- **최적**: 밉맵 있음 + 한 번만 복사 큐로 올려 두고 재사용.
- **볼 것**:
  - 크기를 바꾸는 순간 "처음 만들 때: 픽셀 계산 / 복사 큐 업로드 ms"와 메모리 표의 Default Heap이 바뀝니다. 4K는 256의 256배(64MB)입니다.
  - "매 프레임 새로 만들기"를 켜면 "CPU 작업 ms", "GPU 전체 ms"(복사 포함), 오른쪽 위 그래프, Upload Heap이 함께 오릅니다. 게임의 "로딩 끊김"을 매 프레임 일으키는 셈입니다.
  - 밉맵을 끄면 큐브처럼 작게 보이는 물체도 4K 원본을 읽어 "GPU: 큐브 ms"가 늘고, 멀리 있는 무늬가 지글거립니다. 차이 크기는 GPU마다 다릅니다.
  - "밉 단계마다 색 칠하기"를 켜면 가까운 면은 원래 색, 멀어질수록 초록 → 파랑 → 노랑 → 빨강으로 바뀝니다. "GPU가 작게 보이는 물체에는 작은 판을 골라 읽는다"를 눈으로 보여 주는 장면입니다.
  - 패널 아래 "같은 텍스처를 압축하면: BC7 / BC1" 숫자로 압축 포맷이면 메모리가 1/4, 1/8이 된다는 것을 비교합니다. (실행 중에 압축하지는 않습니다)

### 추천 시연 흐름 (5분)

1. **F2(전부 최적)** 로 시작해서 FPS를 보여 줍니다. "이게 정석대로 만든 상태입니다."
2. **F1(전부 최악)** 을 누릅니다. FPS가 확 떨어집니다. "발표에서 말한 실수를 전부 하면 이렇게 됩니다."
3. 다시 F2를 누른 뒤, 1번부터 하나씩 최악으로 바꿨다 되돌리면서 "어떤 숫자가 움직이는지"를 짚습니다.
4. 마지막으로 9번 VRAM 압박 실험으로 "VRAM 예산을 넘기면 생기는 일"을 보여 줍니다.

### 자주 묻는 질문

**"같은 자리에 반복 그리기"는 무슨 뜻인가요?**
행성을 똑같은 위치에 N번 겹쳐 그립니다. 화면에는 1개로 보입니다. 두 번째부터는 깊이 테스트에 떨어져서 픽셀 칠하기는 거의 생략되지만, 정점 셰이더는 매번 돌아서 정점 데이터를 다시 읽습니다. 그래서 "정점을 어디서 읽느냐"의 비용만 N배로 키워서 보여 줍니다.

**"버퍼를 둘 힙"의 버퍼가 화면 버퍼인가요?**
아닙니다. 행성 모양 데이터(꼭짓점 위치, 법선, UV)를 담은 **정점 버퍼**입니다. 화면 그림이 담기는 백 버퍼는 스왑체인이 만들고 항상 VRAM에 있습니다(8번).

**"정적인 메시"는 가만히 있는 메시인가요?**
아닙니다. **정점 데이터 자체가 안 바뀌는 메시**입니다. 행성은 돌지만, 도는 건 셰이더에 넘기는 회전 행렬이 하는 일이고 꼭짓점 데이터는 그대로입니다. 천 시뮬레이션, CPU 스키닝, 파티클처럼 꼭짓점 자체가 바뀌는 메시(동적 메시)만 매 프레임 보낼 가치가 있습니다.

**화면에 출력까지 했는데 왜 Readback을 하나요?**
Present는 모니터로 보낼 뿐이고 CPU(게임 코드)는 결과를 모릅니다. 스크린샷, 마우스 피킹, 자동 노출(화면 평균 밝기), GPU 물리/오클루전 결과, GPU 시간 측정처럼 CPU가 GPU 결과를 알아야 할 때 씁니다. 이 데모의 "GPU ms"도 Readback 힙으로 받아 읽은 값입니다.

## 4. 패널의 메모리 숫자 읽는 법

| 항목 | 뜻 | 어디서 가져오나 |
|---|---|---|
| **VRAM (Local) 사용 / 예산** | 우리 프로그램이 쓰는 GPU 전용 메모리 / OS가 우리에게 허락한 한도 | `IDXGIAdapter3::QueryVideoMemoryInfo(LOCAL)` |
| **공유 GPU 메모리 (Non-local)** | GPU가 쓰는 메모리 중 시스템 RAM에 있는 것. Upload/Readback 힙이 여기 잡힙니다 | `QueryVideoMemoryInfo(NON_LOCAL)` |
| **시스템 RAM 사용 / 전체** | 컴퓨터 전체 RAM (다른 프로그램 포함) | `GlobalMemoryStatusEx` |
| **정점 / 삼각형 수** | 화면 물체의 정점 수(1번씩 센 값), 이번 프레임 GPU에 보낸 정점 수(반복·인덱스 포함), GPU가 직접 센 정점 셰이더·픽셀 셰이더 실행 횟수. 화면 왼쪽 위에도 표시됩니다 | CPU 계산 + `D3D12_QUERY_TYPE_PIPELINE_STATISTICS` |
| **Working Set / Private** | 지금 RAM에 올라와 있는 우리 프로그램의 메모리 / 우리만 쓰려고 예약한 총량 | `GetProcessMemoryInfo` |
| **우리 앱이 직접 만든 GPU 리소스** | 힙 종류별로 우리가 만든 버퍼/텍스처의 실제 할당 크기 | 직접 집계 (`GetResourceAllocationInfo`) |

> 노트북처럼 **내장 그래픽(UMA)** 이면 VRAM이 따로 없어서 Local과 시스템 RAM이 같은 메모리입니다. 이 경우 1번 시나리오의 차이가 작게 나오는 게 정상입니다. 발표 때는 외장 그래픽카드 PC를 쓰는 것이 좋습니다.

## 5. 용어를 쉽게 풀어 보기

**Upload Heap (업로드 힙)**
- 쉽게 말하면: 우리 집 냉장고. 내가(CPU) 넣기는 쉽지만 요리사(GPU)는 차 타고(PCIe) 와서 가져가야 합니다.
- 뜻: CPU가 쓸 수 있는 시스템 RAM 영역입니다. GPU도 읽을 수 있지만 느립니다.
- 왜 있나: CPU가 만든 데이터를 GPU 쪽으로 보내는 출발점이 필요해서입니다.

**Default Heap (디폴트 힙)**
- 쉽게 말하면: 식당 주방 냉장고. 요리사가 손만 뻗으면 됩니다. 대신 나는 직접 넣을 수 없고, 배달(복사 명령)을 시켜야 합니다.
- 뜻: GPU 바로 옆 VRAM입니다. CPU는 직접 접근할 수 없습니다.
- 예: `CopyBufferRegion(defaultBuf, 0, uploadBuf, 0, size)` 로 Upload → Default 복사.

**GPU Upload Heap / ReBAR (Resizable BAR)**
- 쉽게 말하면: 주방 냉장고에 우리 집에서 바로 넣을 수 있는 배달 창구가 생긴 것.
- 뜻: ReBAR가 켜지면 CPU가 VRAM 전체에 직접 쓸 수 있습니다. `D3D12_HEAP_TYPE_GPU_UPLOAD` 로 이런 버퍼를 만들면 복사 단계가 사라집니다.
- 조건: 메인보드 BIOS에서 ReBAR 켜기, 최신 드라이버, 최신 D3D12 런타임(이 데모는 Agility SDK로 같이 넣음).

**Readback Heap (리드백 힙)**
- 쉽게 말하면: 사진관에서 뽑은 사진을 받아 오는 우편함.
- 뜻: GPU 결과를 CPU가 읽을 수 있게 시스템 RAM에 받아 두는 힙입니다.

**Copy Queue / Fence (복사 큐 / 펜스)**
- 쉽게 말하면: 복사 큐는 짐만 나르는 전용 트럭이고, 펜스는 "여기까지 끝났음" 번호표입니다.
- 뜻: 복사 큐는 복사 명령만 실행하는 GPU 작업 줄입니다. 펜스는 GPU가 어떤 일을 끝냈는지 CPU가 확인하는 값입니다.
- 이 데모에서: 시작할 때 큐브, 텍스처, 행성 메시를 복사 큐로 VRAM에 올리고 펜스로 기다립니다. 걸린 시간이 1번 항목에 표시됩니다.

**Resource Barrier (리소스 배리어)**
- 쉽게 말하면: 공사장 신호수. 깃발을 들면 앞 작업이 끝날 때까지 모두 멈춥니다.
- 뜻: 리소스의 용도(상태)를 바꾼다고 GPU에 알리는 명령입니다. 필요한 곳에만 써야 합니다.

**Descriptor Heap / Root Signature (디스크립터 힙 / 루트 시그니처)**
- 쉽게 말하면: 디스크립터 힙은 "자료 위치가 적힌 명함 상자"이고, 루트 시그니처는 "셰이더의 좌석 배치표(b0, t0, s0 ...)"입니다.
- 이 데모의 루트 시그니처: b0 = 루트 상수 4개, b1 = 프레임 상수(CBV), t0 = 큐브 데이터(루트 SRV), b2 = 물체별 상수(CBV), t1 = 텍스처(디스크립터 테이블), s0 = 정적 샘플러.

**PSO (Pipeline State Object)**
- 쉽게 말하면: 사진 찍기 전에 맞춰 둔 조명, 배경, 카메라 설정 한 세트.
- 뜻: 셰이더와 블렌드, 깊이, 래스터 설정을 한 덩어리로 미리 굳혀 둔 객체입니다. 만들 때 드라이버가 셰이더를 GPU 기계어로 바꾸기 때문에 비쌉니다.

**Draw Call / Instancing (드로우콜 / 인스턴싱)**
- 쉽게 말하면: 학생 2만 명에게 한 명씩 전화하기 vs 단체 문자 한 번.
- 뜻: 드로우콜은 "이거 그려" 명령 하나이고, 인스턴싱은 같은 메시를 여러 개 한 번에 그리는 방법입니다.

**Frames in Flight (동시에 진행하는 프레임)**
- 쉽게 말하면: 손님 한 명 요리가 다 나와야 다음 주문을 받는 식당 vs 주문을 미리 받아 두는 식당.
- 뜻: CPU가 다음 프레임을 준비하는 동안 GPU가 이전 프레임을 그리게 하는 것입니다. 대신 프레임마다 자원이 따로 있어야 합니다.

**Swap Chain / Present / VSync**
- 쉽게 말하면: 그림판 여러 장을 돌려 쓰는 장치. Present는 "이 그림판 이제 보여 줘", VSync는 "모니터가 그림을 바꾸는 순간까지 기다려".

**Budget / Eviction / Residency (예산 / 내보내기 / 상주)**
- 쉽게 말하면: 우리 반에 배정된 사물함 칸 수(예산), 안 쓰는 짐을 창고로 보내기(Evict), 다시 사물함에 넣기(MakeResident).
- 뜻: OS(VidMm)가 프로그램마다 VRAM 한도를 정해 줍니다. 넘기면 일부를 시스템 RAM으로 밀어냅니다.

## 6. 문제 해결

| 증상 | 해결 |
|---|---|
| `cmake 를 찾지 못했습니다` | `build.bat` 은 vswhere로 VS를 찾아 CMake를 자동으로 불러옵니다. 그래도 이 메시지가 나오면 Visual Studio 설치 관리자에서 **"C++를 사용한 데스크톱 개발"** 워크로드가 설치돼 있는지 확인하세요. 또는 **"x64 Native Tools Command Prompt for VS"** 에서 실행해 보세요 |
| `could not find any instance of Visual Studio` | 설치된 VS 버전과 CMake 생성기 이름이 다를 때 납니다. 새 `build.bat`은 2026(`Visual Studio 18 2026`) → 2022 → Ninja 순서로 자동 시도합니다. 그래도 안 되면 `build` 폴더를 지우고 다시 실행하거나, 방법 B(폴더 열기)를 쓰세요 |
| "Agility SDK를 받지 못했습니다" 경고 | 인터넷이나 회사 방화벽 문제입니다. 그래도 빌드되고 실행됩니다. GPU Upload 힙만 꺼질 수 있습니다. 끄려면 `cmake -S . -B build -DUSE_AGILITY_SDK=OFF` |
| GPU Upload 힙(ReBAR)이 회색 | ① BIOS에서 **Resizable BAR** 와 **Above 4G Decoding** 켜기 ② 그래픽 드라이버 최신으로 ③ exe 옆에 `D3D12` 폴더가 있는지 확인. 지원하지 않는 PC여도 나머지 시나리오는 모두 동작합니다 |
| 한글이 □로 보임 | 맑은 고딕(`C:\Windows\Fonts\malgun.ttf`)이 없는 경우입니다. Windows 한국어 환경이면 보통 있습니다 |
| 노트북에서 1번 차이가 작음 | 내장 그래픽(UMA)이면 정상입니다. Windows 설정 → 디스플레이 → 그래픽에서 이 exe를 "고성능"으로 지정해 외장 GPU를 쓰게 하세요 |
| FPS가 60에서 안 올라감 | VSync가 켜져 있거나, 드라이버 설정(NVIDIA 제어판 등)에서 수직 동기화를 강제로 켠 경우입니다 |
| 파란 화면 `VIDEO_TDR_FAILURE (nvlddmkm.sys)` | GPU가 한 작업에 2초 넘게 걸려 드라이버가 리셋되다 실패한 경우입니다. 최신 버전을 받고, NVIDIA 드라이버를 최신으로 올리세요. 다시 나면 그때 켜져 있던 설정을 알려 주세요 |
| 최악 프리셋에서 너무 느려 조작이 힘듦 | 큐브 개수와 행성 삼각형 수를 줄이거나 F2를 누르세요 |

## 7. 코드 구조 (`src/main.cpp` 한 파일)

> 코드를 어디서부터 봐야 할지 모르겠다면 **[CODE_GUIDE.md](CODE_GUIDE.md)** 를 먼저 보세요. 시나리오마다 봐야 할 함수와 줄을 짚어 두었고, 코드 안에서는 Ctrl+F로 `[시나리오 N]` 을 찾으면 바로 그 자리로 갑니다.

| 부분 | 하는 일 |
|---|---|
| `CreateTracked` / `CreateBuffer` | 모든 GPU 리소스를 여기서 만들고 힙 종류별 메모리를 집계 |
| `InitD3D` | 장치, 큐(Direct + Copy), 펜스, 스왑체인, 디스크립터 힙, 프레임 자원 3세트 |
| `CreateRootSignature` / `CreatePso` | 루트 시그니처(b0, b1, t0, b2, t1, s0)와 PSO 두 개 (A와 B는 DepthBias만 다름) |
| `RebuildMesh` | 1번 시나리오: 힙 종류와 재전송 여부에 따라 행성 버퍼를 다시 만듦 |
| `RenderFrame` | 한 프레임: 펜스 대기 → UI → CPU 데이터 준비 → 명령 기록 → 제출/Present → 측정 |
| `DrawPanel` | 오른쪽 패널과 모든 쉬운 설명 툴팁 |
| `ApplyPressure` / `SetPressureResidency` | 9번 VRAM 압박 실험 (할당, Evict, MakeResident) |
| `RebuildTexture` / `GenerateTexturePixels` / `StageAndRecordTextureCopy` | 10번 텍스처: 픽셀과 밉맵 만들기, Upload 임시 상자 → 복사 큐 → VRAM, SRV |

셰이더는 파일 안에 문자열로 들어 있고, 실행할 때 `D3DCompile` 로 컴파일합니다. 그래서 따로 셰이더 빌드 단계가 없습니다.

사용한 라이브러리: [Dear ImGui](https://github.com/ocornut/imgui) 1.92.6 (MIT, `third_party/imgui`), D3D12 Agility SDK 1.619.6 (빌드할 때 자동으로 받음).
